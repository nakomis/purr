# Purr: design

**Date:** 22 November 2026. **Status:** approved by Martin (22 Nov), build in progress.
**Prefix:** `PURR`. **Replaces:** Plane CE on Mace and ATC.

Purr keeps the parts of Plane that are actually used (projects, tasks, states, labels, comments, links,
relations, sub-tasks), turns Plane's modules into first-class **Epics** that span projects, builds in ATC's
priorities board, and drops the rest. It is API-first: in the 30 days before this design every work item and
comment was written by Claude or BAU. Its web UI is a small read-only window whose front page is the
priorities board. It runs on AWS as Lambdas over DynamoDB, with hybrid (vector plus full-text) search from an
index file in S3 and Bedrock Titan embeddings. All storage is behind interfaces, so moving to a relational
database later is a rewrite of the data layer only.

## 1. Why

Martin wants persistence to be cloud-native rather than dependent on boxes in the house. Plane is a set of
long-running services (Django, Celery workers and beat, RabbitMQ, Redis, a WebSocket server, three Next.js
front ends): about $90 a month as always-on containers; a lift-and-shift was ruled out. Purr rebuilds only
what is used, as a native serverless app.

What Plane's data showed (22 Nov 2026):

| Feature | Rows | Purr |
|---|---|---|
| Work items, projects, states | 2,016 items in 51 projects; 333 states | Core ("tasks") |
| Labels | 1,079 labels; 5,193 assignments | Core |
| Comments | 2,538 | Core |
| Modules | 109 (641 memberships) | Become Epics |
| Links, relations, sub-items | 360; 69; 81 | Core |
| Priorities (ATC) | 748 sized items; ordered columns | Core, built in |
| Priority, due dates | 200 set; 4 dated | Priority kept; due dates dropped |
| Cycles, views, pages, attachments | 2; 2; 20; 3 | Dropped (pages exported to Markdown) |
| Estimates, intake, webhooks | 0; 0; 0 | Dropped |

In the last 30 days Claude created 102 items and 115 comments, BAU 80 comments, Martin none in the browser;
about 11,000 API calls a week. Martin uses the UI for an overview and to look things up. The JOBS project is
archived, not migrated.

**ATC** (nakomis/atc) is the priorities layer: three hand-ordered columns (Backlog, Up next, In progress) of
project and module cards, story points on every open item (1 point is about a day of Martin's own work), and
project metadata Plane cannot store (repository, deploy method, deploy action, BAU enabled). It is
authoritative for Claude and BAU ("what's next?"). In Purr the board is the front page and "what's next" is an
ordinary endpoint.

## 2. Goals, non-goals, anti-goals

**Goals:** everything Claude, BAU and Martin do with Plane and ATC, through one agent-first API; Epics as
first-class from day one; every active project's history carried across with refs unchanged; a read-only UI
(board front page, project view, epic view, task page, search; board ordering the only editing); hybrid
search; serverless (nothing billed when idle); a data layer replaceable by a relational one.

**Non-goals (day one):** editing screens beyond board ordering; cycles, estimates beyond points, intake, saved
views, wiki, webhooks, email; multiple workspaces; users beyond Martin, Claude and BAU; searching conversation
memory.

**Anti-goals:** a Plane clone; DynamoDB leaking into the domain; losing a ref or its history; writes that wait
on search; creeping fixed cost (no NAT gateways, always-on databases or search clusters).

## 4. Domain model

Storage-neutral types in `@purr/domain`. IDs are ULIDs generated by the domain. Task refs are allocated per
project; epic refs (`EPIC-n`) from one counter; both atomically. "Task" is the domain word (Plane's work item).

| Entity | Fields (abridged) | Notes |
|---|---|---|
| Project | id, prefix (unique, e.g. HOME), name, description, states, labels, next sequence, metadata (repo, deployMethod, deployAction, bauEnabled), icon, archived | One workspace |
| State | id, name, group (backlog, unstarted, started, completed, cancelled), order | Per project |
| Task | ref, project (exactly one), sequence, projectRank, title, description (Markdown), stateId, labels, parent, priority, points, links, relations, epics, created/updated by and at, version | version = optimistic concurrency |
| Comment | id, taskRef, body (Markdown), author, createdAt | Searchable on its own |
| Relation | type (blocks, blocked_by, relates_to, duplicate_of), target ref | Stored on both tasks, written together |
| Epic | ref (EPIC-n), name, description, state (open, done, archived), projects (set of project IDs it covers), created/updated | Belongs to no project |
| Epic membership | epicRef, taskRef, rank | Many-to-many; rank per membership |
| Board card | kind (project or epic), id, column (backlog, up_next, in_progress), rank | Rank strings sort lexically |
| Activity | taskRef, actor, action, changed fields, at | Append-only |
| Actor | martin, claude, bau, system | |

Descriptions are Markdown; the migration converts Plane's HTML once and keeps the original on the activity record.

### Epics, and the two kinds of ordering

- A task belongs to one and only one project and has a rank in that project's ordering.
- An epic belongs to no project; it can hold tasks from any number of projects, and a task can be in any
  number of epics.
- An epic is flagged on the projects it covers (zero or more), stored as a set of project IDs on the epic.
  Adding a task flags its project in the same atomic write (no-op if already flagged). A project can be
  flagged with no tasks (API only, no UI yet). Removing the last task from a project does not unflag it;
  unflagging a project that still has tasks in the epic is refused (Conflict).
- Each membership carries its own rank: a task's position in an epic is independent of its project position
  and of other epics. Moving a task within an epic rewrites only that membership.
- The board holds project cards and epic cards side by side. A project card lists open tasks in project
  order; an epic card lists open members in epic order.
- Card totals include a task wherever it appears; column totals count each task once.
- "What's next" walks the board: In progress then Up next, cards in order, tasks in each card's order; a task
  is taken the first time it appears. Completed and cancelled tasks are skipped.

## 5. API

JSON over HTTPS (API Gateway HTTP API). Lists use opaque cursors. Errors: `{ "error": { "code", "message" } }`
with 400 (validation), 401, 403, 404 (not found), 409 (conflict / version mismatch).

| Area | Operations |
|---|---|
| Tasks | `GET /tasks/{ref}`; `GET /projects/{prefix}/tasks?state=&label=&epic=&cursor=` (project order); `POST /projects/{prefix}/tasks`; `PATCH /tasks/{ref}` (with version); `POST /tasks/{ref}/pick-up`; `POST /tasks/{ref}/state`; `POST /projects/{prefix}/tasks/reorder` |
| Structure | `PUT/DELETE /tasks/{ref}/labels/{name}`; `POST/DELETE /tasks/{ref}/links`; `POST/DELETE /tasks/{ref}/relations`; `PUT /tasks/{ref}/parent`; `GET /tasks/{ref}/children` |
| Comments | `GET/POST /tasks/{ref}/comments` |
| Projects | `GET /projects`; `GET/PATCH /projects/{prefix}`; `POST /projects`; `GET /projects/{prefix}/epics` |
| Epics | `GET/POST /epics`; `GET/PATCH /epics/{ref}`; `GET /epics/{ref}/tasks` (epic order); `PUT/DELETE /epics/{ref}/tasks/{taskRef}`; `POST /epics/{ref}/tasks/reorder`; `PUT/DELETE /epics/{ref}/projects/{prefix}`; `GET /tasks/{ref}/epics` |
| Priorities | `GET /board[?all=true]`; `POST /board/move`; `PUT /tasks/{ref}/points`; `GET /next`; `GET /priority` |
| Search | `GET /search?q=&mode=hybrid|semantic|fulltext&project=&epic=&kind=task|comment|epic` |
| History | `GET /tasks/{ref}/activity` |

(The design PDF wrote `/items/`; the implementation uses `/tasks/` to match the domain word.)

## 6. Code architecture: storage behind interfaces

```
api (handlers) --> domain (types, rules, services) --> ports (storage, search, embedder, events)
                                                          ^
        storage-dynamo, search-s3, embedder-bedrock ------+   (later: storage-postgres)
```

- One-way dependencies; each Lambda entry builds adapters and injects them.
- Enforced by `scripts/check-boundaries.mjs` (dependency-cruiser refuses Node 25): only `storage-dynamo` imports `@aws-sdk/client-dynamodb` /
  `@aws-sdk/lib-dynamodb`; only `embedder-bedrock` imports the Bedrock runtime client; `domain` imports no AWS
  SDK at all.
- Interfaces shaped by use (no generic query builder). Atomicity inside repository methods; handlers never
  start transactions.
- Neutral contracts: opaque cursors; domain errors (NotFound, Conflict, VersionMismatch, AlreadyExists,
  Validation); rank strings; consistency per method (get-by-ref and board read-after-write; lists and search
  may lag).
- Denormalisation is an adapter detail. `Epics.listByProject` is a scan of epics in DynamoDB.
- No database-only features in the domain: indexing is driven by domain events, never DynamoDB Streams.

Packages (pnpm workspace): `packages/domain`, `packages/contracts`, `packages/storage-memory`,
`packages/storage-dynamo`, `packages/search` (engine + S3 index adapter), `packages/embedder-bedrock`,
`apps/api`, `apps/web`, `apps/mcp`, `tools/migrate-plane`, `infra`.

Tests: contract suites run against `storage-memory` and against `storage-dynamo` on DynamoDB Local; Vitest for
packages and web, Jest for CDK; at least 70% coverage.

## 7. Hybrid search

Documents: each task (title + description), comment and epic. One index file in S3: int8-quantised 1,024-dim
vectors plus a BM25 keyword index (MiniSearch). The search Lambda loads it once per warm instance and fuses
results with Reciprocal Rank Fusion. Embeddings: `amazon.titan-embed-text-v2:0` (eu-west-2). Indexing is
asynchronous: domain events to SQS, an indexer Lambda embeds, caches vectors per document, and writes a fresh
snapshot. Ports: `SearchIndex` and `Embedder`; a search contract suite proves meaning-only and exact-term
queries.

## 8. Cloud architecture

eu-west-2; sandbox (975050268859) and prod (637423226886). API Gateway HTTP API + TypeScript Lambdas outside a
VPC; DynamoDB on demand with PITR; S3 (index, vectors, exports, web); SQS + indexer; Bedrock Titan v2;
CloudFront + S3 for the web (viewer-request function for SPA routing; no distribution-wide errorResponses);
the shared Cognito pool for Martin (per-client managed-login branding; the UI sends the ID token); one API key
per agent (Claude, BAU), stored hashed, checked by a Lambda authoriser that also accepts Cognito JWTs;
`purr.nakomis.com` / `purr.sandbox.nakomis.com` (API under `/api` on the same distribution); SSM under
`/purr/{env}/`; CloudWatch alarms. Estimated $1 to $3 a month per account.

## 9. Migration from Plane and ATC

Read Plane's Postgres on Mace (`172.29.0.3:5436`, database `plane`, schema `atc`) directly; write through the
domain's ports (never straight to DynamoDB); idempotent, dry-run, verification report. Moves: active projects
with states, labels, tasks (refs and counters preserved, project order from Plane's sort order), descriptions
(HTML to Markdown), comments, links, relations, parents, activity, ATC's columns, ranks, points and metadata.
Modules become epics flagged on their project, ordered by ATC's order where present. JOBS and pages are
exported to an archive.

## 10. Clients and cutover
